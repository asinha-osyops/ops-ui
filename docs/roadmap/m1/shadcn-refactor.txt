Refactoring Plan: Migrate Custom Components to shadcn Components

 Overview

 This plan outlines a comprehensive refactoring effort to migrate 20+ custom UI components to use
  shadcn/ui primitives. The goal is to reduce custom code, improve consistency, enhance
 accessibility, and leverage the shadcn ecosystem.

 Estimated Effort: 15-20 development days
 Risk Level: Medium-High (due to widely-used components and complex business logic)

 ---
 Component Analysis Summary

 After exploring the codebase, I identified:
 - 57+ shadcn/ui components available in the library
 - 30+ custom components in the codebase
 - 20+ components that should be refactored to use shadcn primitives
 - 4 components that should remain as-is (infrastructure/already using shadcn)

 Risk Mitigation

 High-Risk Components

 1. DetailField (47 usages) - Refactor component first, test all call sites
 2. CompanySelector (global state) - Test global state integration thoroughly
 3. LogLinesTable (complex logic) - Incremental refactor, extensive manual testing
 4. BulkEmployeeTableEditor (editing) - Test all validation rules

 API Compatibility Requirements

 - DetailField: Must maintain label, value, className, valueClassName, mono props
 - CompanySelector: Must maintain useAppContext integration
 - List components: Must maintain onDelete, onDownload callbacks
 - Table components: Must maintain expandable row functionality

 Breaking Changes to Avoid

 - Do NOT change component APIs without updating all call sites
 - Do NOT remove business logic (employee resolution, validation, etc.)
 - Do NOT break global state integration
 - Preserve all existing functionality

 ---
 Success Criteria

 1. Code Reduction: 30-40% reduction in custom component code
 2. Consistency: 100% of UI uses shadcn primitives
 3. Accessibility: All components pass ARIA checks (shadcn is accessible)
 4. No Regressions: All existing functionality works identically
 5. Maintainability: New developers can reference shadcn docs

 ---
 Recommended Approach

 Execute in phases as outlined above:
 1. Start with Phase 1-2 (simple replacements, cards) to establish patterns
 2. Tackle Phase 3 (DetailField) - critical dependency
 3. Then Phases 4-5 (lists, selectors) using established patterns
 4. Finally Phase 6 (complex tables) with extensive testing
 5. Cleanup in Phase 7

 Alternative: Could refactor incrementally during feature work, but this spreads risk over longer
  timeline.

 Recommendation: Phased approach with dedicated focus ensures consistency and allows for thorough
  testing.
